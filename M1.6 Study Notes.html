1 Slide content — Time Intelligence (1.6.a) slides

  • Turn off auto date/time. Power BI's built-in "Auto date/time" setting silently creates a hidden calendar table for every date column in the model — wasteful, and not best practice. Disable it globally (Options → Global → Data Load) and per-file (Options → Current File → Data Load), under "Time intelligence."
  • A date table is required for any of DAX's time-intelligence functions to work — built in DAX, Power Query, or SQL. All dates in the range must be present (no gaps), and fiscal calendars are possible via CALENDARAUTO(fiscalYearEndMonth).
  • CALENDARAUTO() vs. CALENDAR():
    • CALENDARAUTO([fiscalYearEndMonth]) automatically spans every date-formatted column in the entire model — convenient, but exactly why a stray unrelated date column can blow out the range (see §2 below).
    • CALENDAR(startDate, endDate) — the explicit, preferred form — anchored to the date column that actually matters.
  • Standard date-table build pattern from the slides: 
    DimDate =
ADDCOLUMNS (
    CALENDAR ( MIN ( Sales[Order Date] ), MAX ( Sales[Order Date] ) ),
    "Year", YEAR ( [Date] ),
    "Quarter", FORMAT ( [Date], "\QQ" ),
    "Month", FORMAT ( [Date], "mmmm" ),
    "Month Number", MONTH ( [Date] ),
    "WeekDay", FORMAT ( [Date], "dddd" ),
    "WeekDay Number", WEEKDAY ( [Date] )
)
  • Marking a date table: best practice always; required whenever the relationship between the date table and a fact table uses a key column that isn't itself formatted as a date (a surrogate integer key, for instance) — this comes up directly in §5 and §6 below.
  • Year-to-date: CALCULATE(SUM(Sales[SalesAmount]), DATESBETWEEN('Date'[Date], DATE(YEAR(MAX('Date'[Date])),1,1), MAX('Date'[Date]))) — equivalently, CALCULATE(SUM(Sales[SalesAmount]), DATESYTD('Date'[Date])).
  • Same period last year: DATEADD('Date'[Date], -1, YEAR) ⇔ SAMEPERIODLASTYEAR('Date'[Date]) — the latter is just the named one-year-back special case of the former, which works for any period (DAY/MONTH/QUARTER/YEAR) and either direction.
  • Running total needs an explicit date filter, comparing every date to the last visible date in the current context: 
    SalesAmountRT :=
VAR LastVisibleDate = MAX ( 'Date'[Date] )
RETURN
    CALCULATE (
        SUM ( Sales[SalesAmount] ),
        FILTER ( ALL ( 'Date' ), 'Date'[Date] <= LastVisibleDate )
    )
  • Combining time-intelligence functions: CALCULATE(SUM(Sales[SalesAmount]), DATESYTD(SAMEPERIODLASTYEAR('Date'[Date]))) — YTD, as of the same point last year.

2 Demo — Date table demo demo/exercise

1.6.b - date table demo.srt. File model: a Sales table (100,000 rows) and a Receipts table (90,000 rows), both transaction tables, both sliced by a single shared Date table on the one side of a one-to-many relationship.

2.1 Why CALENDARAUTO() over-reached

The date table started out built like this:

Date =
ADDCOLUMNS (
    FILTER (
        CALENDARAUTO (),
        YEAR ( [Date] ) >= YearFirstOrder
    ),
    -- Year/Quarter/Month/etc. columns...
)
-- where YearFirstOrder = YEAR ( MIN ( Sales[Order Date] ) )

With the FILTER(... YEAR([Date]) >= YearFirstOrder) wrapper in place, this produced 1,461 rows, correctly starting from 2007 — matching the sales table's actual minimum Order Date of January 2, 2007.

Live experiment: comment out the filter

With just CALENDARAUTO() and no year filter, the date table balloons to 36,890 rows, reaching all the way back to 1910. Why? CALENDARAUTO() scans every date-formatted column in the entire data model — not just Sales[Order Date] — and the culprit turned out to be Customer[Birth Date], which had a value back in 1910. A completely unrelated dimension column silently expanded the calendar by nearly a century.

Rule

This is exactly why the slides recommend the explicit CALENDAR(start, end) form over CALENDARAUTO() for anything beyond a quick prototype — larger date tables cost real memory, and CALENDARAUTO()'s "scan everything" behavior is a silent, easy-to-miss source of bloat.

2.2 Rebuilding with CALENDAR(), anchored correctly

Task posed mid-video (pause and try it yourself): replace CALENDARAUTO() with CALENDAR(startDate, endDate), where the start date is January 1 of the year of the first sale, and the end date is December 31 of the year of the last sale.

Date =
ADDCOLUMNS (
    CALENDAR (
        DATE ( YEAR ( MIN ( Sales[Order Date] ) ), 1, 1 ),
        DATE ( YEAR ( MAX ( Sales[Order Date] ) ), 12, 31 )
    ),
    -- same Year/Quarter/Month/etc. columns as before
)

Verified against the underlying Sales table: minimum Order Date = Jan 2, 2007; maximum Order Date (in this specific demo file) landed at the end of December 2009 — and the rebuilt date table's range matched exactly, start to end.

2.3 Marking the date table

Table Tools → Mark as date table, select the date column, click OK. In this demo the primary/foreign key pair used for the relationship was already a proper date-typed column, so marking it here is "necessary and good practice" but not strictly load-bearing yet. The video explicitly flags that there are cases where the key isn't date-typed, and marking becomes required — that case shows up directly in §5 and §6.

3 Demo — Common time intelligence functions demo/exercise

1.6.c - common time intelligence functions.srt, file: 1.6.c 06 Mixing time intelligence functions.pbix. Framing point made up front: a Sales Amount number sliced by year/month/date is meaningless without a benchmark — you need something comparable, like "what happened last year," before you can call a number good or bad.

3.1 Same period last year

Sales SPLY := CALCULATE ( [Sales Amount], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
MonthSales AmountSales SPLYYoY %
Jan 2007$794K——
Jan 2008$656K$794K−17%

January 2007's total ($794K) shows up exactly one year later as January 2008's Sales SPLY value, giving a direct YoY comparison — January 2008 was down about 17% versus the same month a year earlier.

3.2 Year-to-date, and combining it with SPLY

Sales YTD := CALCULATE ( [Sales Amount], DATESYTD ( 'Date'[Date] ) )
-- e.g., context = February 2008 → sums Jan 1, 2008 through Feb 29, 2008 → $1.2M

Sales YTD Last Year :=
CALCULATE ( [Sales Amount], DATESYTD ( SAMEPERIODLASTYEAR ( 'Date'[Date] ) ) )
-- take the current context's dates, shift them a year back, THEN take year-to-date of that shifted range

The video notes this could equally be written with explicit variables (get the current dates → shift them a year → compute YTD on the shifted set), but the nested-function form does the same thing more compactly, and is the version actually used in the file.

3.3 Running total — why it never resets

The same Sales RT pattern as the slides (VAR LastVisibleDate = MAX('Date'[Date]), then CALCULATE([Sales Amount], FILTER(ALL('Date'), 'Date'[Date] <= LastVisibleDate))) is walked through concretely:

Why FILTER(ALL(...)) doesn't need a lower bound

For the September 2011 row, the matrix's own context filter would normally restrict dates to Sept 1–30, 2011. But CALCULATE's filter arguments overwrite the existing context rather than intersect with it — so the FILTER(ALL('Date'), 'Date'[Date] <= LastVisibleDate) argument completely replaces that Sept 1–30 window with just "on or before Sept 30, 2011." There's no lower bound left at all, so the sum always reaches back to the very first sale in the model — which is exactly the running-total behavior wanted.

4 Demo & exercise — Creating a date table for two fact tables demo/exercise

1.6.d - creating a date table.srt. Two separate problems to solve in this file: (1) the date table needs to support two transaction tables (Internet Sales and Reseller Sales) at once, and (2) neither table's date key is actually formatted as a date.

4.1 Problem 1 — the date keys are whole numbers, not dates

OrderDateKey, DueDateKey, and ShipDateKey are all stored as plain whole numbers in the form YYYYMMDD (e.g., 20070102). Trying to just change the column's data type to Date directly in Power BI throws an error — there's no automatic conversion path from an integer like that to a real date.

Fix, done in Power Query ("Transform Data"), for each fact table:

  1. Select the key column (e.g., OrderDateKey) and change its type to Text first.
  2. Add Column → Custom Column, name it Order Date, with the formula: 
    Order Date = Date.FromText ( [OrderDateKey] )
  3. Explicitly set the new column's type to Date (even though Power Query may already infer it correctly — being explicit avoids Power BI silently importing it as text instead).
  4. Repeat the same three steps on the other fact table.
  5. Home → Close & Apply to bring the new date columns back into the model.
Rule

Some data-shaping tasks are genuinely easier in Power Query than in DAX (and vice versa) — the professor's advice: be comfortable moving between the two rather than forcing everything into DAX.

4.2 Problem 2 — one date table, two source tables

The date range now has to span whichever table has the earliest and latest sale, across both fact tables:

Date =
ADDCOLUMNS (
    CALENDAR (
        DATE (
            YEAR (
                MIN ( MIN ( 'Internet Sales'[Order Date] ), MIN ( 'Reseller Sales'[Order Date] ) )
            ), 1, 1
        ),
        DATE (
            YEAR (
                MAX ( MAX ( 'Internet Sales'[Order Date] ), MAX ( 'Reseller Sales'[Order Date] ) )
            ), 12, 31
        )
    ),
    -- Year / Quarter / Month / Month Number / WeekDay / WeekDay Number columns...
)
The nested MIN/MAX pattern

MIN and MAX do double duty: the inner calls (MIN('Internet Sales'[Order Date])) each scan a whole column for its minimum; the outer call just compares the two resulting scalar values against each other and returns the smaller. Same function, two different jobs, depending on whether its arguments are a column or two already-computed values.

4.3 Finishing the date table and wiring it up

  • Format the Date column as Date (not Date/Time).
  • Set sort-by columns: Month sorts by Month Number, WeekDay sorts by WeekDay Number — and hide both numeric helper columns from report view, since end users have no reason to see or slice by them.
  • Mark as date table.
  • Build the relationships: put the Date table in the model between the two fact tables, relating its Date column to each fact table's new Order Date column.
Building the combined Total Sales measure

Create a dedicated _Measures table, then:

Sales = SUM ( 'Internet Sales'[Sales Amount] ) + SUM ( 'Reseller Sales'[Sales Amount] )

No SUMX needed here — Sales Amount is already a stored per-line total (not a unit price needing multiplication), so a plain SUM of each table is enough; report it in a matrix by Year and Month, confirmed to slice correctly with months in calendar order once the sort-by column is set.

5 Solution walkthrough — Time intelligence exercises demo/exercise

1.6.e - solutions of the exercises.srt. Two parts, continuing from the file built in §4.

5.1 Part 1 — SPLY, YTD, YTD-last-year, running total

Sales SPLY := CALCULATE ( [Sales], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
-- verified: December 2011 SPLY value = December 2010's actual sales

Sales YTD := CALCULATE ( [Sales], DATESYTD ( 'Date'[Date] ) )
-- Jan 2011 = ~$2M; Feb 2011 adds ~$466K on top; keeps accumulating through the year, resets to zero in January of the next year

Sales YTD Last Year := CALCULATE ( [Sales], DATESYTD ( SAMEPERIODLASTYEAR ( 'Date'[Date] ) ) )
-- verified: Feb 2012's YTD-Last-Year value = Feb 2011's own YTD value, exactly
Sales RT :=
VAR LastVisibleDate = MAX ( 'Date'[Date] )
RETURN
    CALCULATE (
        [Sales],
        FILTER ( ALL ( 'Date' ), 'Date'[Date] <= LastVisibleDate )
    )
Exercise: restrict the running total to "since 2012"

Naive approach: add a second filter on each fact table's own Order Date column being ≥ 2012 — but that means writing (and maintaining) two separate conditions, one per fact table. Simpler: since the shared Date table already has a single Year column both fact tables are related through, add one extra condition on that instead.

Sales RT since 2012 :=
VAR LastVisibleDate = MAX ( 'Date'[Date] )
RETURN
    CALCULATE (
        [Sales],
        FILTER ( ALL ( 'Date' ), 'Date'[Date] <= LastVisibleDate ),
        'Date'[Year] >= 2012
    )

Result: no running total shown before 2012; from 2012 onward it accumulates normally and does not reset to zero at the next year boundary.

5.2 Part 2 — Reseller Sales YTD: a measure that "isn't working," except it is

New file, existing DimDate already related to FactResellerSales — no new date table needed here, just new measures.

Reseller Sales := SUM ( FactResellerSales[Sales Amount] )
Reseller Sales YTD := CALCULATE ( [Reseller Sales], DATESYTD ( DimDate[Full Date Alternate Key] ) )

(Note: in this dataset the date table's actual date-typed column is named Full Date Alternate Key, not Date — its DateKey column, used as the relationship's key, is a surrogate integer, not a date.)

Bug: Reseller Sales YTD returns identical numbers to plain Reseller Sales

The measure itself is correct — right function, right date column in the filter argument. Rule of thumb invoked directly: when a dataset is new to you, check the data model first, before assuming the DAX is wrong.

Root cause #1 (partial fix): DimDate ↔ FactResellerSales actually has three relationships (via DueDateKey, OrderDateKey, and ShipDateKey). Power BI had auto-activated DueDateKey on import — essentially arbitrarily — instead of OrderDateKey. Deactivating Due Date and activating Order Date changed the numbers slightly, but Reseller Sales and Reseller Sales YTD still matched each other exactly. Not the real bug.

Root cause #2 (the actual fix): DimDate was never marked as a date table. Its relationship key (DateKey) is a surrogate integer, not the actual date column (Full Date Alternate Key) that DATESYTD is being pointed at. Whenever the relationship's key column isn't itself the date column your time-intelligence function uses, marking the date table is not optional — it's required for functions like DATESYTD to work at all. Marking it fixed the measure immediately, with no code change.

6 Demo & exercise — USERELATIONSHIP demo/exercise

1.6.f - USERELATIONSHIP.srt, file: 1.6.f 05b Using multiple dates - USERELATIONSHIP.pbix. Framed explicitly: USERELATIONSHIP is a filter modifier, not a time-intelligence function — it doesn't require a date-typed column at all, just the two key columns of an already-defined (but inactive) relationship.

6.1 Demo: Sales Amount vs. Delivered Amount

Sales Amount := SUMX ( Sales, Sales[Quantity] * Sales[Net Price] )   -- sliced by whichever Date relationship is active (here: Order Date)

Delivered Amount :=
CALCULATE (
    [Sales Amount],
    USERELATIONSHIP ( 'Date'[Date], Sales[Delivery Date] )
)
Rule

USERELATIONSHIP only works if the relationship it names already exists in the model as an inactive relationship — it cannot create a relationship on the fly. Here, Date ↔ Sales[Delivery Date] must already be defined (dashed line) for this to work at all.

Sales Amount doesn't reference the relationship directly in its own code, but it's still sliced by whichever relationship is active at query time (Order Date, by default here). Delivered Amount temporarily swaps which relationship is active for just that one calculation — same underlying Sales rows, sliced by a different date field.

6.2 Exercise: total sales + total shipped sales, across two fact tables

Task: build Total Sales Amount (Internet + Reseller) and Total Shipped Sales Amount (same total, but sliced by ship date instead of order date) — with a hint that this needs two relationship modifiers, one per fact table, since both fact tables independently relate to Date.

Total Sales Amount := SUM ( 'Internet Sales'[Sales Amount] ) + SUM ( 'Reseller Sales'[Sales Amount] )

Total Shipped Sales Amount :=
CALCULATE (
    [Total Sales Amount],
    USERELATIONSHIP ( 'Internet Sales'[ShipDateKey], 'Date'[DateKey] ),
    USERELATIONSHIP ( 'Reseller Sales'[ShipDateKey], 'Date'[DateKey] )
)
Rule

CALCULATE accepts multiple filter arguments/modifiers at once, comma-separated — nothing stops you from activating two different relationships (on two different fact tables) inside the same CALCULATE call.

Prerequisite cleanup performed first (same pattern as §5): each fact table actually had three possible date relationships (order/due/ship), so the default active one had to be checked and, where necessary, switched to Order Date for Total Sales Amount to mean what it's supposed to mean; and DimDate had to be (re-)marked as a date table.

Sanity check on the result

December 2010 shows Sales but zero Shipped Sales (those orders ship in 2011 — orders precede shipments, so this is expected, not a bug). Symmetrically, January 2014's orders are the last ones in the dataset, but February 2014 shows meaningful shipped-sales activity — fulfillment of that January backlog. A story that makes business sense is itself a form of validation for a USERELATIONSHIP-based measure.

7 Example DAX code — consolidated reference

-- Explicit date table anchored to real transaction dates, spanning two fact tables
Date =
ADDCOLUMNS (
    CALENDAR (
        DATE ( YEAR ( MIN ( MIN ( 'Internet Sales'[Order Date] ), MIN ( 'Reseller Sales'[Order Date] ) ) ), 1, 1 ),
        DATE ( YEAR ( MAX ( MAX ( 'Internet Sales'[Order Date] ), MAX ( 'Reseller Sales'[Order Date] ) ) ), 12, 31 )
    ),
    "Year", YEAR ( [Date] ),
    "Month", FORMAT ( [Date], "mmmm" ),
    "Month Number", MONTH ( [Date] ),
    "WeekDay", FORMAT ( [Date], "dddd" ),
    "WeekDay Number", WEEKDAY ( [Date] )
)

-- Converting a YYYYMMDD integer key to a real date (in Power Query, not DAX)
-- 1. Transform → change type to Text
-- 2. Add Column → Custom Column:
Order Date = Date.FromText ( [OrderDateKey] )
-- 3. explicitly set the new column's type to Date

-- Year-to-date, same period last year, and combined
Sales SPLY         := CALCULATE ( [Sales], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
Sales YTD          := CALCULATE ( [Sales], DATESYTD ( 'Date'[Date] ) )
Sales YTD Last Year := CALCULATE ( [Sales], DATESYTD ( SAMEPERIODLASTYEAR ( 'Date'[Date] ) ) )

-- Running total, with and without a start-year floor
Sales RT :=
VAR LastVisibleDate = MAX ( 'Date'[Date] )
RETURN
    CALCULATE ( [Sales], FILTER ( ALL ( 'Date' ), 'Date'[Date] <= LastVisibleDate ) )

Sales RT since 2012 :=
VAR LastVisibleDate = MAX ( 'Date'[Date] )
RETURN
    CALCULATE (
        [Sales],
        FILTER ( ALL ( 'Date' ), 'Date'[Date] <= LastVisibleDate ),
        'Date'[Year] >= 2012
    )

-- USERELATIONSHIP: activate an inactive relationship for one calculation
Delivered Amount :=
CALCULATE ( [Sales Amount], USERELATIONSHIP ( 'Date'[Date], Sales[Delivery Date] ) )

-- USERELATIONSHIP with two modifiers at once, across two fact tables
Total Shipped Sales Amount :=
CALCULATE (
    [Total Sales Amount],
    USERELATIONSHIP ( 'Internet Sales'[ShipDateKey], 'Date'[DateKey] ),
    USERELATIONSHIP ( 'Reseller Sales'[ShipDateKey], 'Date'[DateKey] )
)

  • Can you convert a YYYYMMDD-style whole-number key into a real date column using Power Query, without looking it up?
