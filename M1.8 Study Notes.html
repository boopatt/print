1 Module page — review summary module page

This module has no slide deck of its own — its entire content is the review. The professor's framing, verbatim in spirit: "You should aim to develop a good level of comfort in all these topics as you work with DAX before taking the first exam. The real measure of understanding of these topics is whether you can write DAX code to get the analysis you want with ease."

General principles, called out explicitly

Format your code. Use variables to store scalar values or tables to simplify your code and make it readable. Do not create unnecessary measures or calculated columns. And a specific, testable rule about variables: a variable's use may be required in a nested row context (e.g., inside a calculated column) or when a context filter sits on a measure that itself uses a row context internally — outside of those cases, VAR is a readability choice, not a requirement.

Evaluation contexts

—

Row context: exists in calculated columns, iterators, and FILTER. Allows direct reference to the columns of the table it's defined in, and to the one-side of a relationship via RELATED. Can nest (a calculated column's FILTER opens a second, inner row context).

—

Filter context: defined by implicit filters (a matrix's row/column) and explicit filters (report filter, slicer). Relationship filters propagate according to cross-filter direction.

—

Variable use: may be required in a nested row context, or when a context filter sits on a measure that uses a row context internally. In most other cases it's a readability choice, not a requirement.

CALCULATE — the rules, restated

1

Computes its first argument, subject to any filter argument(s).

2

The first argument can't directly reference a column name; filter arguments can.

3

Can overwrite filters — use KEEPFILTERS where you need to intersect instead of replace.

4

Can use a table variable as a filter argument.

5

Does not accept aggregations directly in its filter arguments, and never needs FILTER wrapped around a simple boolean condition there.

6

Performs context transition. Can also modify filters via USERELATIONSHIP and CROSSFILTER.

Time intelligence

Date table via CALENDARAUTO or CALENDAR (CALENDAR is the preferred/more controllable choice) → mark as date table → define sort-by columns for text fields → hide unnecessary columns from report view → set up relationships. Common calculations: year-to-date, quarter-to-date, month-to-date; same period last year/quarter/month; running total.

Table queries

—

FILTER — to apply boolean filters, or filters that involve an aggregation; has a row context.

—

CALCULATETABLE — to evaluate a table expression or apply boolean filters; no row context of its own; applies context transition.

—

ADDCOLUMNS — to add columns to a table; combine with SUMMARIZE to add an aggregation to a group of selected columns.

—

GENERATE — returns the Cartesian product between each row of table1 and the table that results from evaluating table2 in the context of that row.

—

TOPN — returns the top N rows of a table by some expression.

3 Exercise 1.8.a — walkthrough exercise

File: AdventureWorks.pbix. First step: create a measures table and name it _Measures (the underscore prefix/suffix pattern keeps it sorted to the top of the table list — the same pattern introduced informally back in M1.2).

3.1 Verify LineTotal and SubTotal, two ways each

Is OrderDetail[LineTotal] really quantity × price? Is OrderHeader[SubTotal] really the sum of LineTotal? Build both comparisons on a multi-row card rather than assuming a stored column means what its name implies.

Revenue (LineTotal) = SUM ( OrderDetail[LineTotal] )

Revenue (discounted unit price) =
SUMX (
    OrderDetail,
    OrderDetail[Quantity] * OrderDetail[UnitPrice] * ( 1 - OrderDetail[Discount] )
)

Revenue (SubTotal) = SUM ( OrderHeader[SubTotal] )

See §4 below — in this dataset, all three land on the exact same number, which is itself worth confirming rather than assuming.

3.2 Average quantity sold per order — with and without RELATEDTABLE

-- Without RELATEDTABLE: average directly over OrderHeader, pulling in a per-order total via CALCULATE
Avg Order Quantity (no RELATEDTABLE) =
AVERAGEX (
    OrderHeader,
    CALCULATE ( SUM ( OrderDetail[Quantity] ) )
)

-- With RELATEDTABLE: explicitly walk to each order's related line items
Avg Order Quantity (RELATEDTABLE) =
AVERAGEX (
    OrderHeader,
    SUMX ( RELATEDTABLE ( OrderDetail ), OrderDetail[Quantity] )
)
Why both work

CALCULATE(SUM(...)) inside an iterator performs context transition — the current OrderHeader row becomes a filter on OrderDetail, which is exactly what RELATEDTABLE does explicitly. They're two spellings of the same mechanism (this is the CALCULATE/RELATEDTABLE equivalence from M1.5).

3.3 Total cost of goods sold

COGS = SUMX ( OrderDetail, OrderDetail[Quantity] * RELATED ( Product[StandardCost] ) )

3.4 DAX query — top 3 products by margin %, per category

Required output: five columns — category name, product name, revenue, cost of goods sold, margin. Use DISTINCT instead of VALUES to avoid blank rows from any unmatched foreign keys leaking into the result (the same DISTINCT/VALUES distinction from M1.3, applied here as a practical fix rather than a theory question).

EVALUATE
GENERATE (
    DISTINCT ( Product[Category] ),
    TOPN (
        3,
        ADDCOLUMNS (
            DISTINCT ( Product[Product Name] ),
            "Revenue", CALCULATE ( SUMX ( OrderDetail, OrderDetail[Quantity] * OrderDetail[UnitPrice] * ( 1 - OrderDetail[Discount] ) ) ),
            "COGS",    CALCULATE ( SUMX ( OrderDetail, OrderDetail[Quantity] * RELATED ( Product[StandardCost] ) ) ),
            "Margin",  DIVIDE ( [Revenue] - [COGS], [Revenue] )
        ),
        [Margin]
    )
)

3.5 Effective discount rate, then "highly discounted" sales two ways

Effective Discount Rate =
VAR ActualRevenue      = SUMX ( OrderDetail, OrderDetail[Quantity] * OrderDetail[UnitPrice] * ( 1 - OrderDetail[Discount] ) )
VAR UndiscountedRevenue = SUMX ( OrderDetail, OrderDetail[Quantity] * OrderDetail[UnitPrice] )
RETURN
    DIVIDE ( UndiscountedRevenue - ActualRevenue, UndiscountedRevenue )
Exercise, as given

A product is "highly discounted" if its effective discount rate across all its sales exceeds 30%. First build the total sales for highly discounted products using the Effective Discount Rate measure; then build it a second time without using that measure — doing everything inline in one measure. Hint given directly in the exercise: make sure context transition is taking place whenever an aggregation runs row-by-row. Finally: how would the measure change if you wanted highly discounted line items instead of highly discounted products?

-- Via the helper measure
Highly Discounted Product Sales =
SUMX (
    FILTER (
        VALUES ( Product[Product Name] ),
        CALCULATE ( [Effective Discount Rate] ) > 0.30
    ),
    CALCULATE ( SUMX ( OrderDetail, OrderDetail[Quantity] * OrderDetail[UnitPrice] * ( 1 - OrderDetail[Discount] ) ) )
)

-- Self-contained, one measure, no helper
Highly Discounted Product Sales 2 =
SUMX (
    FILTER (
        VALUES ( Product[Product Name] ),
        VAR ActualRevenue =
            CALCULATE ( SUMX ( OrderDetail, OrderDetail[Quantity] * OrderDetail[UnitPrice] * ( 1 - OrderDetail[Discount] ) ) )
        VAR UndiscountedRevenue =
            CALCULATE ( SUMX ( OrderDetail, OrderDetail[Quantity] * OrderDetail[UnitPrice] ) )
        RETURN
            DIVIDE ( UndiscountedRevenue - ActualRevenue, UndiscountedRevenue ) > 0.30
    ),
    CALCULATE ( SUMX ( OrderDetail, OrderDetail[Quantity] * OrderDetail[UnitPrice] * ( 1 - OrderDetail[Discount] ) ) )
)

Both versions need an explicit CALCULATE around every aggregation inside the outer FILTER's row context (iterating over VALUES(Product[Product Name])) — that's context transition turning "the current product" into an actual filter before SUMX can run against OrderDetail. Drop any one of those CALCULATEs and every product silently gets evaluated against the grand-total discount rate instead of its own. For line items instead of products: drop the outer FILTER-over-VALUES entirely and just filter OrderDetail rows directly by a per-line-item discount rate — no context transition is needed at all once you're filtering at the same grain you're aggregating.

What this confirms

All three revenue formulations agree exactly — in this dataset, LineTotal, the recomputed discounted-price calculation, and OrderHeader's SubTotal are all internally consistent, so the "verify, don't assume" exercise pays off by confirming the stored columns are trustworthy here (that won't always be true in other datasets — check anyway). The average-order-quantity measures agree regardless of RELATEDTABLE vs. context-transition phrasing, exactly as the mechanism predicts. And critically: both "highly discounted" measures land on the identical $96,670,410 — if your two versions disagree, one of them is missing a context-transition CALCULATE somewhere in the row-by-row aggregation.

Sanity check the discount rate arithmetic yourself: 1 − (109,846,381 / 170,964,700) = 35.75% ✓.

5 Key takeaways / self-check

  • Work the exercise cold, under a timer, before checking §4 — that's the actual point of this module.
  • If your revenue numbers don't all match, don't assume the DAX is wrong before checking the data: revisit whether Discount is stored as a fraction (0.15) vs. a whole percent (15) — a unit mismatch here is a classic silent bug.
  • If your two "highly discounted" measures disagree, the fix is almost always a missing CALCULATE around one of the row-by-row aggregations inside the outer FILTER — restate, from memory, why that CALCULATE is required there (context transition, M1.5).
  • If your DAX query returns extra blank rows, switch VALUES to DISTINCT on the offending column before debugging anything else (M1.3).
  • Across all of Module 1: can you now write DAX to answer a new business question directly, instead of pattern-matching to the closest example you've seen? That's the bar this review page sets.
