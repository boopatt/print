1 Slide content — Table Queries (1.7.a) slides

  • EVALUATE <table expression> runs a table expression directly in DAX Query View, outside of any visual. The table expression can be a bare table name or a full nested table query.
  • Table functions revisited as table queries: FILTER, ALL, VALUES, and DISTINCT all already return a table, so they can stand alone under EVALUATE. RELATEDTABLE cannot — it requires an existing row context (from an iterator or calculated column) to know which "current row" to relate from, so it only makes sense nested inside something that already supplies one.
  • CALCULATETABLE: the table-returning counterpart to CALCULATE. Applies filter arguments to a table expression exactly like a slicer would — including performing context transition where needed.
  • ADDCOLUMNS + SUMMARIZE: ADDCOLUMNS appends one or more ad hoc columns to an existing table, each computed in its own row context. SUMMARIZE performs a group-by — pairing the two lets you build a grouped table with an aggregate column in one expression.
  • TOPN: returns the top N rows of a table with respect to a given expression.
  • GENERATE: GENERATE(table1, table2) — for each row of table1, evaluates table2 in that row's context, and stacks the results. Effectively a row-context-aware join with no relationship-traversal syntax required.
  • Combining them: GENERATE wrapping a TOPN is the standard shape for "top N rows per group."

2 Video walkthrough — Table Queries overview video

ISA512 1.7a Table Queries.srt — the lecture companion to the slides, demonstrated in DAX Studio (a free add-in for Excel and a standalone app for Power BI). DAX Studio can query the data model behind either tool and is called out specifically as a good way to export data out of Power BI, something Power BI itself doesn't make easy.

  • EVALUATE is a required keyword — the simplest possible query is just EVALUATE Customer, which dumps the entire table.
  • CALCULATETABLE vs. FILTER, explained directly: CALCULATETABLE doesn't perform aggregation — it's purely a filter on columns that already exist (e.g. CALCULATETABLE(Product, Product[Color]="Red")). FILTER can do that too, but can additionally filter on conditions that involve an aggregation (e.g. Sales Amount > 1000000) — because FILTER supplies a row context, and an aggregation evaluated inside that row context needs context transition to mean anything. That's exactly why a FILTER condition built on a measure needs CALCULATE wrapped around it: "if you don't have calculate there, your filter will not work — it won't perform context transition." CALCULATETABLE doesn't have this problem because it isn't row-context-based in the first place.
  • ADDCOLUMNS is the same function used earlier to build a date table (M1.6) — it takes a table and adds columns to it. Combined with SUMMARIZE, it can group a fact table down to unique combinations of two dimension columns (e.g. Category × Subcategory) and attach a "Sales" aggregate column to each combination in one step. Skip SUMMARIZE if you just want to add a column to a table that's already at the grain you need.
  • TOPN walkthrough: TOPN(10, <table with a Sales column>, [Sales]) — once an ad hoc column (like "Sales") is defined earlier in the same query, it's referenced afterward in square brackets, e.g. [Sales]. Wrapping the whole thing in CALCULATETABLE(..., Product[Color]="Red") gets you the top 10 red products — because CALCULATETABLE's filter applies before TOPN does its ranking.
  • GENERATE walkthrough: think of it as a loop — it iterates the second table once for every row of the first. Demonstrated with GENERATE(VALUES('Product Category'[Category]), RELATEDTABLE('Product Subcategory')): for each distinct category, it retrieves the full set of related subcategory rows and lists them underneath. If you don't need every subcategory column, wrap the RELATEDTABLE call in SELECTCOLUMNS to keep just the one you want.
  • Combining TOPN + GENERATE: GENERATE(VALUES('Product Category'[Category]), TOPN(3, ..., [Sales])) — for every distinct category, find its own top 3 products by total quantity sold. Each category contributes up to 3 rows to the final result (fewer only if it has fewer than 3 products with any sales at all).

3 Exercise — On-time delivery (1.7.c) demo/exercise

1.7.c - exercise (on-time delivery).srt, file: 1.7.c Freight analysis (begin).pbix. Structured as a series of "pause the video and try it yourself" prompts — reconstructed here with the actual DAX reached in each step.

Task 1

Create a measure for OTD % (on-time delivery percent), where on-time is defined as any order whose required date is ≥ ship date. Hint given in the video: it's an average.

OTD % =
AVERAGEX (
    Orders,
    IF ( Orders[Required Date] >= Orders[Ship Date], 1, 0 )
)
The > vs. >= gotcha, caught live

Writing the condition as > instead of >= gives OTD % = 39%; correcting it to >= jumps the result to ~78–79%. Per the business definition, a shipment on the exact required date is on time — a single missing equals sign nearly doubled the reported performance number. A reminder that DAX gives zero warning for this kind of error: both versions run fine, only one is right.

Second issue: sorting the Orders table shows a number of orders with a blank Ship Date (not yet shipped) — these shouldn't count as either on-time or late, so they need to be excluded from the average rather than silently scored as 0. Three equivalent fixes, all confirmed in the video to give the same result (78.61%):

-- A: nested IF, exclude blanks inline
OTD % =
AVERAGEX (
    Orders,
    IF (
        ISBLANK ( Orders[Ship Date] ),
        BLANK (),
        IF ( Orders[Required Date] >= Orders[Ship Date], 1, 0 )
    )
)

-- B: pre-filter the table being iterated
OTD % =
AVERAGEX (
    FILTER ( Orders, NOT ( ISBLANK ( Orders[Ship Date] ) ) ),
    IF ( Orders[Required Date] >= Orders[Ship Date], 1, 0 )
)

-- C: CALCULATE with a filter argument around the original measure logic
OTD % =
CALCULATE (
    AVERAGEX ( Orders, IF ( Orders[Required Date] >= Orders[Ship Date], 1, 0 ) ),
    NOT ( ISBLANK ( Orders[Ship Date] ) )
)

Sliced by Country in a matrix: Canada has the highest OTD %, the United States the lowest.

Task 2

Create OTD % YTD using the time-intelligence functions from M1.6 — the video explicitly expects you to do this unassisted at this point.

OTD % YTD = CALCULATE ( [OTD %], DATESYTD ( 'Date'[Date] ) )

This assumes a working date table — checked and fixed live: Month Number and Weekday Number hidden from report view, Month given Month Number as its sort-by column, Weekday given Weekday Number as its sort-by column, and the table marked as a date table — all M1.6 setup steps, called out here as prerequisites that are easy to forget once you're several modules further in.

Task 3 — this is where table queries actually become necessary

Given an aspired OTD level of 85%, what percent of customers have reached it?

The video's own framing of why a plain measure can't do this: to compute "percent of customers above a threshold" you need OTD % per customer sitting somewhere filterable — if it were a calculated column on the Customer table you could just filter and count. But it can't be a calculated column (it needs an aggregation over Orders). The fix is to build that per-customer table on the fly, inside the measure, with ADDCOLUMNS:

Percent Customers with Aspired OTD =
VAR OTDTable =
    ADDCOLUMNS (
        VALUES ( Customers[Company Name] ),
        "OTD", [OTD %]
    )
VAR NumberAspired  = COUNTROWS ( FILTER ( OTDTable, [OTD] >= 0.85 ) )
VAR NumberCustomers = COUNTROWS ( OTDTable )
RETURN
    DIVIDE ( NumberAspired, NumberCustomers )
Why the denominator isn't just COUNTROWS(Customers)

Counting the entire Customers table would silently assume every customer has at least one order. If there are inactive customers with no sales at all, they shouldn't be in the denominator of an OTD-performance question. Counting rows of OTDTable instead works because that table was already built by iterating over customers who have an OTD % — i.e., customers with at least one order.

Result: about 10% of customers overall. Sliced by country in a matrix (sorted descending): Mexico leads at roughly 18–19%, every other country falls below the 10% line.

4 Solutions — On-time delivery (1.7.d) demo/exercise

1.7.d - solutions to exercise (on-time delivery).srt — three follow-on tasks left as take-home problems in 1.7.c, solved here.

4.1 Percent of products with aspired OTD

Same pattern as the customer version, just swapping the grouping column:

Percent Products with Aspired OTD =
VAR OTDTable =
    ADDCOLUMNS (
        VALUES ( Product[Product Name] ),
        "OTD", [OTD %]
    )
VAR NumberAspired = COUNTROWS ( FILTER ( OTDTable, [OTD] >= 0.85 ) )
VAR NumberProducts = COUNTROWS ( OTDTable )
RETURN
    DIVIDE ( NumberAspired, NumberProducts )

Result: 5% of products. Slicing the underlying product list by Category shows only a handful of categories with any qualifying products at all — Beverages, Condiments, Seafood, Confections (in that order); every other category has zero products meeting the 85% bar.

4.2 Percent of customer–product combinations at a 65% "acceptable" OTD

Here VALUES hits its limit: it can only return distinct values of one column, but this question needs a table keyed by the unique combination of customer and product together. The fix is SUMMARIZE, which can group by more than one column at once:

Acceptable Customer-Product OTD % =
VAR OTDTable =
    ADDCOLUMNS (
        SUMMARIZE ( Orders, Orders[Customer ID], Orders[Item ID] ),
        "OTD", [OTD %]
    )
VAR OTDTableNoBlank = FILTER ( OTDTable, NOT ( ISBLANK ( [OTD] ) ) )
VAR NumberAcceptable = COUNTROWS ( FILTER ( OTDTableNoBlank, [OTD] >= 0.65 ) )
VAR NumberCombinations = COUNTROWS ( OTDTableNoBlank )
RETURN
    DIVIDE ( NumberAcceptable, NumberCombinations )
Rule

Whenever an ad hoc column needs to be computed for a unique combination of more than one column, reach for SUMMARIZE — VALUES and DISTINCT are single-column tools only.

Building the raw SUMMARIZE table first (dropped into a temporary table via Table tools → New table just to inspect it — a good habit called out explicitly: "it's good practice to see what your table variable holds in it") turned up 4,579 rows, several with a blank OTD — customer/product pairs that summarize can produce without a clean matching OTD value. Left uncleaned, those blanks inflate the denominator with combinations that shouldn't count. Filtering both the numerator and the denominator through NOT(ISBLANK([OTD])) first fixes it. Final result: 75% of customer–product combinations meet the 65% acceptable bar.

4.3 Total revenue for customers who hit the aspired OTD — a table query as a CALCULATE filter

The hint from 1.7.c pays off here directly: find the qualifying customer list with a table query, then hand it to CALCULATE as a filter argument.

Aspired OTD Sales =
VAR AspiredOTDCustomers =
    FILTER (
        ADDCOLUMNS ( VALUES ( Customers[Customer ID] ), "OTD", [OTD %] ),
        [OTD] > 0.85
    )
RETURN
    CALCULATE ( [Total Revenue], AspiredOTDCustomers )

Result: roughly $202,000. The variable's table is passed to CALCULATE by name, exactly like any other filter argument — it restricts [Total Revenue] to only the customer keys that survived the FILTER, with no need for the revenue measure itself to know anything about OTD.

5 Exercise — Days of supply (1.7.e) demo/exercise

1.7.e - exercise (days of supply).srt. A second full example of building a table query end to end, this time to compute Daily Sales Units and Days of Supply per product.

5.1 Daily Sales Units — first pass, and the missing-CALCULATE bug

Goal: a table query with one row per date that had any sales, and a column holding that date's total quantity sold — then average across those rows.

Daily Sales Units =
VAR DailySalesTable =
    ADDCOLUMNS (
        VALUES ( Orders[Order Date] ),
        "Quantity Sold", SUM ( Orders[Quantity] )   -- missing CALCULATE — see below
    )
RETURN
    AVERAGEX ( DailySalesTable, [Quantity Sold] )
The same context-transition bug as M1.5, one module later

Checked by materializing DailySalesTable as a real table (Table tools → New table, in Data view — "good practice to see what your table variable holds"): every row showed the identical grand-total quantity instead of that date's own total. Reason: ADDCOLUMNS gives each row a row context, but a bare SUM(Orders[Quantity]) doesn't automatically turn that row context into a filter on Orders — exactly the row-context-vs-filter-context gap first seen with CALCULATE in M1.5. The fix is to wrap the aggregation in CALCULATE to force context transition:

"Quantity Sold", CALCULATE ( SUM ( Orders[Quantity] ) )

With that fix, each date's Quantity Sold correctly reflects only that date's own orders, and AVERAGEX now averages real per-day totals.

5.2 Imputing zero for days with no sales

Days with zero sales don't appear as 0 in DailySalesTable — CALCULATE(SUM(...)) returns BLANK() for them instead, and AVERAGEX (like AVERAGE) silently drops blanks rather than counting them as zero. That inflates the average for any product with sparse sales. Fix: force blanks to zero before averaging.

Daily Sales Units =
VAR DailySalesTable =
    ADDCOLUMNS (
        VALUES ( Orders[Order Date] ),
        "Quantity Sold", CALCULATE ( SUM ( Orders[Quantity] ) )
    )
RETURN
    AVERAGEX (
        DailySalesTable,
        IF ( ISBLANK ( [Quantity Sold] ), 0, [Quantity Sold] )
    )

Noted as a small effect in the aggregate numbers shown live, but a real one for individual low-volume products — the same "blank ≠ zero" caution that showed up in M1.2's delivery-days work, here in the opposite direction (there, blanks correctly needed to be excluded; here, they correctly need to be treated as zero, because "no sales that day" is a real zero, not a missing measurement).

Simpler alternative mentioned in passing (not the table-query approach, shown only for comparison): DIVIDE(SUM(Orders[Quantity]), DISTINCTCOUNT(Orders[Order Date])) — total quantity over the count of distinct selling days. Called out as "simpler," but the video's actual purpose was to demonstrate the table-query technique, so this shortcut is a footnote, not the intended answer.

5.3 Days of Supply

Days of Supply = DIVIDE ( SUM ( Product[Units in Stock] ), [Daily Sales Units] )
Why SUM(Product[Units in Stock]) and not a bare column reference

This is a measure, not a calculated column — there's no row context, so Product[Units in Stock] can't be referenced directly even though, in whatever filter context the measure lands in, there's only a single matching value. It still has to be wrapped in an aggregator (SUM here) to resolve to a scalar. The same expression would work as a bare column reference inside a calculated column on the Product table, precisely because a calculated column supplies the row context this measure doesn't have.

Sanity check: a "syrup" product with ~13 units in stock and ~12 daily sales units comes out to roughly 1 day of supply — checks out.

5.4 Folding it into one self-contained measure — and why not a calculated column

The whole thing collapses into a single measure once Daily Sales Units is inlined as a variable instead of kept as its own measure:

Days of Supply =
VAR DailySalesTable =
    ADDCOLUMNS (
        VALUES ( Orders[Order Date] ),
        "Quantity Sold", CALCULATE ( SUM ( Orders[Quantity] ) )
    )
VAR DailySalesUnits =
    AVERAGEX ( DailySalesTable, IF ( ISBLANK ( [Quantity Sold] ), 0, [Quantity Sold] ) )
RETURN
    DIVIDE ( SUM ( Product[Units in Stock] ), DailySalesUnits )

The video also builds this same logic as a calculated column on the Product table to show that it technically works there too (a calculated column's row context makes Product[Units in Stock] resolvable without SUM) — then explicitly rejects that version:

Why the table-query measure wins over the calculated column

"We don't want it to be a calculated column because we can do it in a measure, and we don't need to create these unnecessary calculated columns — they hold data, they increase the size of our file, and reduce the efficiency." This is the concrete payoff of table queries as a technique: they let you reach a per-row result inside a measure, which is exactly what used to force a calculated column onto the model.

Aside from the module page: total Units in Stock is not summable across time — a stock-on-hand snapshot doesn't add up meaningfully year over year the way a transaction total does, which is part of why this measure is built from Orders (a true transaction table) rather than by trying to aggregate Units in Stock over a date hierarchy.

6 Example DAX code — consolidated reference

-- EVALUATE: the simplest table query
EVALUATE Customer

-- CALCULATETABLE: filter only, no aggregation allowed in the condition
EVALUATE
CALCULATETABLE ( Product, Product[Color] = "Red" )

-- FILTER: row context, so aggregation-based conditions need CALCULATE inside
EVALUATE
FILTER ( Product, CALCULATE ( SUM ( Sales[Quantity] ) ) > 1000 )

-- ADDCOLUMNS + SUMMARIZE: group by, with an aggregate column
EVALUATE
ADDCOLUMNS (
    SUMMARIZE ( Sales, 'Product Category'[Category], 'Product Subcategory'[Subcategory] ),
    "Sales", [Sales Amount]
)

-- TOPN: rank, referencing an ad hoc column defined earlier via square brackets
EVALUATE
TOPN ( 10, ADDCOLUMNS ( VALUES ( Product[Product Name] ), "Sales", [Sales Amount] ), [Sales] )

-- GENERATE: per-row Cartesian join
EVALUATE
GENERATE ( VALUES ( 'Product Category'[Category] ), RELATEDTABLE ( 'Product Subcategory' ) )

-- TOPN + GENERATE: top N per group
EVALUATE
GENERATE (
    VALUES ( 'Product Category'[Category] ),
    TOPN ( 3, ADDCOLUMNS ( VALUES ( Product[Product Name] ), "Sales", CALCULATE ( SUM ( Sales[Quantity] ) ) ), [Sales] )
)

-- Per-entity table built on the fly, then filtered / counted (the OTD pattern)
VAR EntityOTD = ADDCOLUMNS ( VALUES ( Table[Key] ), "OTD", [SomeMeasure] )
VAR Qualifying = FILTER ( EntityOTD, [OTD] >= 0.85 )
RETURN DIVIDE ( COUNTROWS ( Qualifying ), COUNTROWS ( EntityOTD ) )

-- Unique combination of TWO columns needs SUMMARIZE, not VALUES
SUMMARIZE ( Orders, Orders[Customer ID], Orders[Item ID] )

-- A table query used as a CALCULATE filter argument
VAR Qualifying = FILTER ( ADDCOLUMNS ( VALUES ( Table[Key] ), "M", [SomeMeasure] ), [M] > 0.85 )
RETURN CALCULATE ( [TotalRevenue], Qualifying )

-- Context transition inside ADDCOLUMNS' row context — don't forget CALCULATE
"Quantity Sold", CALCULATE ( SUM ( Orders[Quantity] ) )   -- not just SUM(...)

-- Blank-safe averaging where blank really does mean zero
AVERAGEX ( DailySalesTable, IF ( ISBLANK ( [Quantity Sold] ), 0, [Quantity Sold] ) )

7 Key takeaways / self-check

  • Can you state, without looking it up, why CALCULATETABLE can't filter on an aggregation-based condition but FILTER can — and why FILTER needs CALCULATE wrapped around the aggregation to make that work?
  • Given a business question that needs "per-entity value, then filter/count," can you reach for ADDCOLUMNS(VALUES(...), "X", [Measure]) as a table query, rather than reaching for a calculated column you can't actually build?
  • Do you know when VALUES/DISTINCT stop being enough and SUMMARIZE becomes necessary (unique combination of more than one column)?
  • Inside an ADDCOLUMNS row context, can you tell when a bare aggregation like SUM(...) will silently return the grand total instead of a per-row value, and why wrapping it in CALCULATE fixes it? (This is the exact same mechanic as M1.5's context transition, one module later, in a new disguise.)
  • Can you tell, for a given blank value in your data, whether it should be excluded from an average (M1.2's delivery days, M1.7's customer-product OTD) or treated as zero (M1.7's daily sales units) — and explain why those are different situations rather than a contradiction?
  • Can you build a table query, save it as a VAR, and pass it into CALCULATE as a filter argument — and explain why that's different from filtering inside the measure's own aggregation?
